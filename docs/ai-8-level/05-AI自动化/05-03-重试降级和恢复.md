# 5-03 错误处理——重试降级和恢复

欢迎回来。上一集我们学了结构化输出。今天我们聊错误处理——模型超时、限流、输出无效、下游失败时，怎么重试、降级和恢复。

## 自动化中一定会遇到错误

无论你的设计多完善，自动化系统中一定会遇到错误：

模型超时——AI 处理太慢，超过了设定的时间限制。

模型限流——调用频率太高，被服务商限制。

输出无效——AI 的输出不符合 Schema，或者包含了非法值。

下游失败——写入目标系统时超时或返回错误。

这些错误不是"意外"，而是自动化系统的常态。关键不是避免所有错误，而是正确地处理错误。

## 错误分类

错误大致分几类：

输入错误——数据格式不对、缺字段、类型错误。处理方式：直接拒绝，不进入 AI 处理，记录失败原因。

模型错误——调用超时、被限流、输出格式不对。处理方式：有限次重试，超过限制后降级到离线响应或人工队列。

下游错误——写入目标系统时超时或失败。处理方式：先查询操作状态，确认是否成功；如果状态未知，进入待恢复队列，不重复创建。

规则冲突——AI 的分类结果和预设规则矛盾。处理方式：规则优先，AI 输出不能覆盖确定性规则。

## 重试策略

重试不是无限次尝试。每次重试都应该有明确的限制：

最大尝试次数——比如最多 3 次。

单次超时——比如单次调用最多 8 秒。

总截止时间——比如整个任务最多 30 秒。

等待间隔——比如第一次重试等 1 秒，第二次等 2 秒。

比如模型超时的重试策略：

总尝试 3 次，单次超时 8 秒，等待 1、2 秒，总截止 30 秒。

这意味着：第一次调用，等 8 秒超时；等 1 秒后第二次调用，等 8 秒超时；等 2 秒后第三次调用，等 8 秒超时。如果三次都超时，或者总时间超过 30 秒，就停止重试，进入降级或人工队列。

## 降级策略

降级不是失败，而是切换到备用方案。

比如模型持续超时，你可以降级到离线响应——使用预先准备好的固定响应，而不是实时调用模型。

比如搜索工具不可用，你可以降级到人工查找——暂停自动化流程，通知人工介入。

降级的关键是：提前定义好降级方案，不要在错误发生时临时决定。

## 幂等性

幂等性是自动化系统中一个重要的概念。它的意思是：同一个操作执行一次和执行多次，结果是一样的。

比如你提交一个反馈分拣任务，系统创建了一条工单。如果你因为超时重试，系统不应该创建第二条工单。

幂等性通过幂等键实现。每个请求都有一个唯一的幂等键（比如 feedback_id + workflow_version + input_hash）。系统在处理前先检查：这个幂等键是否已经处理过？如果已经成功，直接返回旧结果；如果正在处理，等待或查询状态；如果没有处理过，才创建新记录。

幂等性防止了重复创建、重复扣费等问题。

## 下游失败的处理

写入目标系统时失败，是最复杂的情况之一。因为你可能不知道：写入是否成功？

比如你调用一个 API 创建工单，API 超时了。你不知道：工单是否已经创建？还是根本没有创建？

错误的做法是：立即重试。如果工单已经创建了，重试会创建第二条。

正确的做法是：先查询操作状态。

大多数系统提供状态查询接口。你用幂等键查询：这个操作的状态是什么？

如果状态是 SUCCEEDED，说明工单已经创建，直接返回成功。

如果状态是 PROCESSING，说明还在处理中，等待或稍后查询。

如果状态是 FAILED_RETRYABLE，说明失败但可以重试，用原幂等键重试。

如果状态是 NOT_FOUND，说明没有记录，可以安全重试。

这种"先查询再重试"的模式，防止了重复创建。

## 一个错误处理案例

假设你处理一条客户反馈，模型调用超时了。

错误处理流程：

第一步，记录错误。在日志中记录：feedback_id、错误类型（MODEL_TIMEOUT）、尝试次数、等待时间。

第二步，重试。等待 1 秒后第二次调用，仍然超时。等待 2 秒后第三次调用，仍然超时。总时间超过 30 秒。

第三步，降级。三次重试都失败，切换到离线响应。使用预先准备的固定响应（比如 category="其他"、urgency="中"、requires_human_review=true）。

第四步，记录降级。在日志中记录：使用了离线响应，原因：MODEL_TIMEOUT。

第五步，继续流程。用离线响应继续后续处理（风险判断、写回等）。

## 日志和追踪

每一次错误和处理都应该有日志记录：

```json
{
  "feedback_id": "N01",
  "event": "MODEL_TIMEOUT",
  "attempt": 1,
  "wait_seconds": 0,
  "timestamp": "2026-08-03T10:30:00+08:00"
}
{
  "feedback_id": "N01",
  "event": "MODEL_TIMEOUT",
  "attempt": 2,
  "wait_seconds": 1,
  "timestamp": "2026-08-03T10:30:09+08:00"
}
{
  "feedback_id": "N01",
  "event": "FALLBACK_TO_OFFLINE",
  "reason": "MODEL_TIMEOUT",
  "timestamp": "2026-08-03T10:30:20+08:00"
}
```

日志不仅是事后复盘的工具，也是成本核算和性能优化的依据。
