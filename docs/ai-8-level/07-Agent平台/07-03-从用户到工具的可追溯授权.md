# 7-03 身份链路——从用户到工具的可追溯授权

欢迎回来。上一集我们学了六层架构。今天我们聊身份链路。

## 身份链路的重要性

一个请求从用户发出，经过应用、Agent、平台，最终到达工具和业务系统。在这条链路上，每一步都必须知道：最终用户是谁、哪个 Agent 在处理、Agent 的版本是什么、平台工作负载是什么、工具端如何授权。

如果链路中丢掉了最终用户身份，就无法证明"谁有权做什么"。如果只传最终用户、不验证 Agent 身份，也无法证明"是哪一版 Agent 发起的请求"。

## 身份链路的组成

身份链路包含：

租户或数据域——请求属于哪个租户或数据域？

用户主体——最终用户是谁？

应用——哪个应用在发起请求？

Agent 版本——哪个版本的 Agent 在处理？

工作负载——平台的工作负载标识是什么？

工具——调用哪个工具？

对象——操作哪个业务对象？

批准——谁批准的？

追踪标识——请求的追踪 ID 是什么？

这些信息必须随请求传播，不能在中途丢失。

## 身份链路的挑战

身份链路要处理这些情况：

员工离职后权限是否及时撤销？

员工跨部门调动后数据权限是否更新？

服务账号泄露后能否一键停用？

审计时能否还原批准人和业务对象？

如果身份链路设计不好，这些问题都无法回答。

## 一个身份链路案例

假设用户 U-A 通过客服 Agent 查询订单 ORD-1002。

身份链路：

租户：C-001
用户主体：U-A
应用：客服 Agent
Agent 版本：support-agent-1.0.0
工作负载：platform-workload-001
工具：get_own_order
对象：ORD-1002
批准：U-A（当前轮确认）
追踪标识：TRACE-001

当工具端收到请求时，它可以看到：这个请求来自 U-A，通过客服 Agent v1.0.0，查询 ORD-1002。工具端验证：U-A 是否有权查询 ORD-1002？如果有权，返回结果；如果无权，拒绝。

审计时，可以通过 TRACE-001 还原整个链路：谁在什么时候通过什么 Agent 查询了什么订单。

## 身份链路的实现

身份链路的实现需要：

认证网关——验证用户身份，注入用户主体和客户引用。

Agent 服务身份——Agent 以自己的服务身份调用平台，不冒充用户。

工具端验证——工具端验证调用方的身份和权限，不信任上游的声明。

追踪标识——每个请求携带唯一的追踪 ID，贯穿整个链路。

认证网关只依据 Bearer Token 或服务端会话解析用户身份，再映射客户引用。两者都不进入模型参数。任何外部身份头必须在网关入口剥离。

## 共享账号的风险

共享账号是身份链路的敌人。

如果多个用户共用一个服务账号，就无法证明"谁在什么时候做了什么"。审计时无法还原批准人，出问题无法追责。

平台应该禁止共享账号。每个用户、每个 Agent、每个工作负载都应该有独立的身份。
