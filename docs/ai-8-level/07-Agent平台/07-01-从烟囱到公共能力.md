# 7-01 为什么需要平台——从烟囱到公共能力

欢迎回到 AI 使用能力系列。从这一级开始，我们进入第 7 级——Agent 平台。

前六个级别我们解决了从个人对话到单个 Agent 应用的问题。这一级我们要把视角拉高——当一个企业有多个 Agent 应用时，怎么避免重复建设、统一治理、降低成本。

## 为什么需要平台

先看一个典型场景。一家企业有三个 Agent 项目：客服 Agent、内部知识助手和研发 Agent。三个团队各自采购模型、各自建设知识处理、各自接入身份系统、各自保存日志、各自维护评测。

结果是什么？

三个团队都在做知识切分和索引，但做法不同，标准不同。三个团队都接入了身份系统，但传递身份的方式不同。三个团队都有日志，但请求编号不统一，出了问题需要 3 个多小时才能把跨系统的事件拼起来。三个团队各自和模型供应商谈价格，但加起来的需求量本来可以拿到更好的条件。

这就是"烟囱式建设"的问题。不是说每个团队做得不好，而是他们在重复做同样的事情，而且互相之间没有统一的接口和标准。

平台要解决的就是这个问题：识别公共能力，统一标准和接口，让各业务团队在统一控制面上建设自己的 Agent。

## 平台不是什么

在说平台是什么之前，先说平台不是什么。

平台不是把所有业务逻辑收进一个中央团队。平台提供的是稳定契约和自助能力，业务团队仍然对自己的业务结果负责。

平台不是买一个产品就完事了。采购获得的是能力供给，不会自动获得数据治理、流程优化、评测和治理能力。

平台不是统一实现。统一接入不等于统一实现。不同业务有不同的数据域、业务规则和权限要求，平台要尊重这些差异。

## 公共能力的判据

哪些能力应该平台化？四个判据：

复用——多个应用都需要这个能力。

风险一致性——这个能力的风险特征在多个应用中相似。

契约稳定性——这个能力的接口不容易变化。

规模经济——集中建设比分散建设成本更低、质量更好。

比如模型接入、身份认证、日志追踪、成本核算——这些能力多个应用都需要，风险特征相似，接口稳定，集中建设有规模经济。这些应该平台化。

比如客服的回复模板、研发的代码规范——这些是业务特定的，不应该平台化。

## 第 7 级的学习目标

第 7 级要让你掌握四个能力：

第一，从多个 Agent 项目中识别真正需要平台化的公共能力与必须保留的业务个性。

第二，设计模型、数据与知识、工具、编排、应用和治理六层架构。

第三，建立身份权限、租户隔离、工具准入、发布评测、成本配额、审计与容灾机制。

第四，根据企业数据、团队和业务条件比较采购、联合建设、自建和混合部署。
