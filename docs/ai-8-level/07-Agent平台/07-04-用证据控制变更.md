欢迎回来。前三集我们学了平台认知、六层架构和身份链路。今天我们聊发布门禁。

## 为什么需要发布门禁

平台必须控制 Agent 的变更发布。

模型版本更新、知识库修改、工具权限变化、提示词调整——每一种变更都可能影响 Agent 的行为。你不能只做一个演示就说"可以上线了"。

## 发布门禁的组成

发布门禁应该包括：

G0 登记——记录变更内容、版本、负责人。

G1 契约——确认接口和依赖没有破坏性变化。

G2 离线评测——用标准样本集测试新版本的表现。

G3 安全测试——验证高风险请求是否仍然被拦截。

G4 影子运行——新旧版本同时运行，比较结果差异。

G5 灰度发布——先在小范围上线，观察指标。

G6 生产发布——全量上线。

G7 退役——旧版本下线。

## 高风险样本单独判定

高风险样本必须单独判定，不能用平均分掩盖。

一个 Agent 在 99% 的普通场景表现完美，但在 1% 的高风险场景失败——这不能通过"平均分 99 分"来证明它合格。

高风险样本包括：退款请求、改址请求、取消请求、补偿请求、人身安全、敏感身份信息、权限不足、提示注入。

这些样本必须 100% 拦截。如果新版本在任何一个高风险样本上失败，就不能上线。

## 回滚标准

发布前必须定义回滚标准：哪个指标下降会自动回滚？

比如：高风险拦截率下降、任务成功率下降、成本上升超过阈值——这些都应该触发自动回滚。

回滚不是"以后再修"，而是"立即回到上一个稳定版本"。

## 紧急变更

紧急变更可以走预定义紧急流程，但不能跳过身份、审计和回滚。

紧急变更后必须补审，最长补审时限必须明确。
