## 为什么需要工具调用

除了回答问题，Agent 通常还需要执行一些操作——查询订单、创建工单、发送通知等。

这些操作通过"工具"实现。工具是 Agent 和外部系统交互的接口。

## 工具清单

每个工具都有明确的类型、副作用、权限和失败行为。

比如：

search_public_knowledge——只读，允许，无副作用，失败时诚实说明。

get_own_order——只读，允许，无副作用，失败时不猜测状态。

create_case_draft——低风险写入，受控允许，创建草稿，失败时查幂等状态。

create_handoff——写入，允许，创建接管单，失败时保留草稿。

refund_order——高风险，无工具、禁止执行，只创建人工接管单。

change_order——高风险，无工具、禁止执行，只创建人工接管单。

cancel_order——高风险，无工具、禁止执行，只创建人工接管单。

你看，工具分为三类：只读、低风险写入、高风险（禁止执行）。

高风险操作（退款、改址、取消、补偿）不提供执行工具。Agent 只能创建人工接管单，由人工来决定和执行。

## 工具契约

每个工具都有明确的输入、输出、副作用、权限和失败处理方式。

比如 get_own_order：

输入：order_id（订单编号）

输出：订单状态、追踪信息、预计时间

副作用：无（只读）

权限：只能查询当前用户自己的订单

失败行为：不猜测状态，不泄露存在性

再比如 create_case_draft：

输入：conversation_id、case_intent_id、order_id、category、summary 等

输出：draft_id、replayed

副作用：在系统中创建一条记录

权限：需要用户当前轮明确确认

失败行为：查幂等状态，结果未知则接管

## 身份和权限

Agent 在调用工具时，它代表谁？它能看到什么数据？它能做什么操作？

正确答案是：Agent 的身份和权限应该来自经过认证的用户身份，而不是来自用户自己在对话中声称的身份。

比如用户说"我是客户 C-001，帮我查一下订单 ORD-1003"。Agent 不能直接信任这句话。它应该从认证系统中获取当前用户的身份，然后检查这个用户是否有权查看这个订单。

如果认证身份是 C-002，那 ORD-1003 不属于这个用户，Agent 应该拒绝查询——而且不能告诉用户"这个订单存在但不属于你"，因为这也泄露了信息。

## 确认语义

创建案例草稿前，必须取得用户的明确确认。

什么算"明确确认"？只有当前轮明确说"确认创建"才算。沉默、历史同意和模糊表达均不算确认。

比如：

Agent："我为您创建一个案例草稿，内容是...，确认创建吗？"

用户："确认。" → 可以创建。

用户："好的。" → 模糊，需要再次确认。

用户：（沉默）→ 不创建。

用户：（历史对话中说过"同意"）→ 不算，必须当前轮确认。

一次确认只对应一次草稿。如果摘要变化，旧确认作废，需要重新确认。

## 幂等性

写操作必须幂等。同一个意图执行一次和执行多次，结果是一样的。

比如你创建一个案例草稿，系统返回 draft_id。如果你因为超时重试，系统不应该创建第二个草稿。

幂等性通过幂等键实现。每个请求都有一个唯一的幂等键（比如 conversation_id + case_intent_id + confirmed_summary_hash + agent_version）。系统在处理前先检查：这个幂等键是否已经处理过？如果已经成功，直接返回旧结果。

## 工具失败的降级

工具调用可能失败：超时、返回错误、结果未知。

失败时的处理：

只读工具（search_public_knowledge、get_own_order）——重试有限次，仍失败则诚实说明并接管。

写入工具（create_case_draft、create_handoff）——先查幂等状态，状态未知则接管，不重复创建。

高风险操作——不提供工具，只创建接管单。

工具失败时，Agent 不应该用知识猜实时状态。比如订单工具失败了，Agent 不应该说"根据经验，您的订单可能已发货"，而应该说"当前无法核实订单状态，已创建人工接管单"。
